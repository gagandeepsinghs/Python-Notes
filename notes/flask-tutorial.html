Flask, end to end

Flask is a small Python web framework. It gives you routing, templating and a request object, then stays out of the way. Everything else — database, forms, login — you add when you need it.

This guide goes from an empty folder to a tested, deployable application: routing, Jinja templates, forms, sessions, SQLAlchemy, authentication, a JSON API, and a production checklist. Every snippet runs on Flask 3.x and Python 3.9+.

Chapter 1

What Flask is

Flask is a microframework. The "micro" means it ships with a small core and no opinions about your database, your form library or your project layout. It is built on two libraries by the same team:

  • Werkzeug — the WSGI layer: request and response objects, URL routing, the development server.
  • Jinja — the template engine that turns .html files plus data into finished pages.

A Flask app is a Python object that maps URLs to functions. When a request arrives, Flask matches the URL, calls your function, and turns whatever you return into an HTTP response. That is the whole model, and everything in this guide is a variation on it.

When to reach for it

Flask suits APIs, small-to-medium sites, prototypes, internal tools and anything where you want to choose your own pieces. Django is the better fit when you want an admin interface, an ORM and auth decided for you on day one. FastAPI is the better fit when you are building a typed, async-first JSON API and want automatic OpenAPI docs.

Vocabulary you will see

WSGI is the Python standard for talking between a web server and a Python app. Route is a URL pattern. View function is the function that handles a route. Endpoint is the name Flask gives a view so you can build URLs for it.

Running it

Open http://127.0.0.1:5000. If your file is named app.py or wsgi.py, you can shorten this to flask run --debug.

Routing and URLs

Building URLs with url_for

Never hard-code links. url_for takes the view's name and builds the URL, so changing a route in one place fixes every link to it. Extra keyword arguments become the query string.

Trailing slashes

A rule written as /projects/ also answers /projects with a redirect to the canonical slashed form. A rule written as /about returns 404 for /about/. Pick one style and keep to it.

Treat everything in request as hostile

Chapter 6

Jinja templates

Put HTML files in a templates/ folder next to app.py and render them with render_template. Keyword arguments become variables inside the template.

Syntax

Jinja has two delimiters: {{ }} prints a value, {% %} runs a statement.

Inside a loop, loop.index (1-based), loop.index0, loop.first, loop.last and loop.length are available.

Filters

A filter transforms a value with |. They chain.

Autoescaping

Jinja escapes <, > and & in every variable it prints, which is what stops cross-site scripting. |safe switches that off for one value. Only use it on HTML you generated yourself, never on anything a user typed.

Inheritance

One base layout, many pages that fill in its blocks. This is the single most useful Jinja feature.

Includes and macros

include pastes another template in. A macro is a reusable function that outputs markup.

Chapter 7

Static files

CSS, JavaScript, images and fonts go in a static/ folder. Flask serves them at /static/… automatically in development.

myapp/ ├── app.py ├── templates/ │ ├── base.html │ └── posts.html └── static/ ├── style.css ├── app.js └── img/logo.svg

Browsers cache aggressively. During development, hard-refresh if a stylesheet change does not appear. In production, put a version in the URL (style.css?v=3) or let a build tool add a content hash to the filename.

Chapter 8

Forms

A plain HTML form posts to a route; you read request.form, validate, then redirect. The pattern below — render on GET, process on POST, redirect on success, re-render with errors on failure — is the backbone of every form in Flask.

Flask-WTF

For anything beyond a couple of fields, Flask-WTF defines the form once as a class and handles validation, re-rendering and CSRF protection.

What CSRF protection does

Without it, another site can make a logged-in visitor's browser submit a form to yours. Flask-WTF puts a secret token in each form and rejects submissions that do not carry it. It needs SECRET_KEY to be set.

Chapter 9

Sessions and flash messages

HTTP has no memory between requests. The session object gives you one: it behaves like a dict, and Flask stores it in a cookie that is cryptographically signed with your SECRET_KEY.

Signed, not encrypted

Anyone holding the cookie can read its contents; they just cannot change it without the key. Keep passwords, tokens and personal data out of the session — store an ID and look the rest up server-side. Generate a key with python -c "import secrets; print(secrets.token_hex(32))" and keep it out of version control.

Flash messages

A flash is a one-shot message stored in the session and displayed on the next page — the "Saved." banner after a redirect.

Config and the app factory

Settings live on app.config, a dict with a few helpers for loading values from elsewhere.

Keeping secrets in a .env file

With python-dotenv installed, the flask command loads .env automatically. Under a production server, call load_dotenv() yourself or set real environment variables.

The application factory

Instead of creating app at import time, create it inside a function. This lets you build one app configured for production and a different one for tests, and it removes the circular-import problems that appear once a project has more than one module.

Extensions are created empty here and bound to an app inside the factory with init_app. Run it with flask --app "app:create_app" run --debug.

Chapter 12

Blueprints and project structure

A blueprint is a group of routes, templates and static files that gets registered onto an app. Think of it as a section of the site — auth, blog, admin — in its own module.

Endpoints inside a blueprint are namespaced by its name, so links use url_for("blog.show", post_id=1). Inside a template belonging to the same blueprint you can shorten that to url_for(".show", post_id=1).

Chapter 13

Databases with SQLAlchemy

Flask-SQLAlchemy maps Python classes to database tables. Start on SQLite, which needs no server, and switch the connection string later to move to Postgres.

Creating the tables

create_all() only creates tables that do not exist; it will not alter an existing one. Once the schema starts changing, move to migrations (next chapter).

Querying

Nothing is saved until you commit

add() stages an object; commit() writes the transaction. If something fails mid-way, call db.session.rollback() before using the session again.

Chapter 14

Migrations

A migration is a versioned script that changes the database schema. Flask-Migrate wraps Alembic and compares your models to the live database to generate them.

Always read the generated script

Autogeneration misses some changes — renamed columns look like a drop plus an add, which destroys data. Open the file in migrations/versions/ and correct it before upgrading, and take a backup before running migrations in production.

Chapter 15

Authentication

Two parts: store passwords as hashes, and track who is logged in. Werkzeug supplies the hashing; Flask-Login supplies the session handling.

Never store a raw password, and never email one back to a user. A hash is one-way: you can check a guess against it, but you cannot recover the original.

Give the same message for a wrong email and a wrong password, so the form cannot be used to discover which addresses are registered.

Chapter 17

File uploads

The form needs enctype="multipart/form-data"; the file arrives in request.files.

Uploads are user input too

Store files outside the folder your web server executes from, never trust the client's filename or content type, and set MAX_CONTENT_LENGTH so a large upload cannot exhaust memory. On most hosts the local disk is temporary — use object storage for anything that must survive a restart.

Chapter 18

Hooks, g and the application context

Hooks run around every request in the app or blueprint they are registered on.

g is a scratchpad that lives for exactly one request — a good place to cache the current user or an open connection, and a bad place for anything that should outlive the response.

The two contexts

Flask pushes an application context (which powers current_app and g) and a request context (which powers request and session). Inside a view both exist. Outside one — in a script, a shell, a background job — you have to push one yourself, which is the cause of the familiar "working outside of application context" error.

Chapter 20

Testing

Flask's test client makes requests without a running server. With an app factory, each test gets a fresh app pointed at a throwaway database.

Run everything with pytest -q. To inspect the session inside a test, use with client.session_transaction() as sess:.

Chapter 21

Deployment

The development server handles one thing at a time and is not hardened. In production, a WSGI server runs your app and a reverse proxy sits in front of it terminating TLS and serving static files.

A reasonable worker count is (2 × CPU cores) + 1. On Windows, use waitress-serve --port=8000 wsgi:app instead.

Behind a proxy

Nginx or your platform's load balancer forwards the original scheme and client IP in headers. Tell Flask to trust them, or url_for(_external=True) will generate http:// links and request.remote_addr will be the proxy.

Before you go live

  • SECRET_KEY comes from the environment and is long and random.
  • DEBUG is off. The interactive debugger must never be reachable from the internet.
  • Session cookies are Secure, HttpOnly and SameSite=Lax; the whole site is on HTTPS.
  • Migrations have been applied, and you have a tested database backup.
  • Static files are served by the proxy or a CDN, not by Python.
  • MAX_CONTENT_LENGTH is set; uploads go to object storage.
  • Logs go somewhere you will actually read, and unhandled errors reach an error tracker.
  • Login, signup and password reset are rate limited (Flask-Limiter).
  • Dependencies are pinned in requirements.txt.

Where to go next

Useful extensions once the basics are in place: Flask-Limiter for rate limiting, Flask-Mail for outbound email, Flask-Caching for page and query caching, Celery or RQ for background jobs, and Flask-Admin for a quick CRUD interface over your models.
